# LRN-007 — `/api/health` flappait Down/Up : seuil de fraîcheur == fréquence cron + instance RPi jamais mise à jour

| Pattern observé                                                                                                                              | Contexte                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Application future                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Uptime Kuma alertait "degraded"/404 par intermittence sur `/api/health`, avec des cycles Down→Up à ~5min d'écart (ex. 18:05 Down → 18:10 Up) | Deux causes cumulées : (1) `CACHE_MAX_AGE_MS` (2h) utilisé tel quel comme seuil de staleness, alors que le cron ETL tourne exactement toutes les 2h (`0 */2 * * *`) ET que le `fetch` de `metadata.json` dans la route a `revalidate: 300` — juste après un run ETL, la route pouvait encore lire le `last_updated` du run précédent (via le cache Next 5min) et déclarer "degraded" pendant qu'un vrai run venait de se terminer ; (2) l'instance RPi (`pm2: faistonplein`, self-hosted en plus de Vercel) tournait un commit **24 en retard**, antérieur à l'ajout même de la route `/api/health` — 404 garanti tant que non déployé | Un seuil de fraîcheur alimenté par un cron régulier doit toujours inclure une marge > (intervalle du cron le plus flou + durée du cache de fetch en amont), jamais juste être égal à l'intervalle nominal — voir GLRN-199 (mémoire globale, même famille de bug côté config Kuma). Fix appliqué : `HEALTH_STALE_THRESHOLD_MS = CACHE_MAX_AGE_MS + 30min`. Par ailleurs, une instance self-hosted (RPi) à côté de Vercel doit être vérifiée en `git log HEAD..origin/main` avant tout diagnostic de monitoring — elle peut driver silencieusement pendant des mois (ici via `pm2` sans auto-deploy) et devenir la vraie source d'un 404 qu'on attribuerait à tort à Vercel |

**Détail additionnel** : le process `faistonplein` sur le RPi tourne `next dev --turbo -p 3000 --experimental-https` (script `dev:https`), pas `next start` — c'est un serveur dev auto-signé HTTPS, pas un build de prod. `pnpm build` n'est donc pas strictement nécessaire pour ce process (il recompile à la volée), mais un `pm2 restart` après un `git pull` reste indispensable pour qu'il reprenne les nouveaux fichiers de route.
